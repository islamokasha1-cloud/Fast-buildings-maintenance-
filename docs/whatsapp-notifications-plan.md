# خطة تصميم: إشعارات واتساب للفنيين وطلبات الشراء

> وثيقة تخطيط (Design Doc) — لا كود إنتاجي بعد. الهدف: إرسال إشعارات واتساب
> (١) للفنيين لإشعارهم بالبلاغات المُسندة إليهم، و(٢) للمعنيين بطلبات الشراء
> لتنبيههم بطلب جديد أو بطلبٍ ينتظر اعتمادهم حسب صلاحياتهم.

---

## 0) الخلاصة التنفيذية (TL;DR)

- **المشكلة الجوهرية:** النظام حالياً **client-side بالكامل** (SPA + Firebase، بلا خادم خلفي).
  واتساب يتطلب استدعاء API خارجي بتوكن سرّي — **لا يمكن فعله من المتصفح** دون كشف السر.
  لذا الميزة تفرض إضافة **طبقة خلفية جديدة**.
- **المعمارية المقترحة:** **Firebase Cloud Functions (2nd gen)** بمشغّلات Firestore
  (Firestore-triggered) + **Secret Manager** لحفظ توكن واتساب + **صندوق صادر `wa_outbox`**
  كطابور موثوق للإرسال مع إعادة المحاولة ومنع التكرار.
- **مزوّد واتساب:** الأنسب **WhatsApp Cloud API من Meta** (رسمي، طبقة مجانية).
  بديل أسرع للإعداد: **Twilio WhatsApp** (أغلى لكن أبسط). كلاهما يتطلب
  **قوالب رسائل معتمَدة مسبقاً** (Message Templates) للرسائل المُبادِر بها العمل.
- **بيانات ناقصة يجب إضافتها:** لا يوجد **رقم هاتف** مخزَّن لأي فني أو مستخدم.
  يجب إضافة حقل `phone` (+ موافقة opt-in) إلى `technicians` و`USERS`.
- **نقاط الإطلاق:** مشغّلات على Firestore بدل نمط `onSnapshot` الحالي (الذي يتطلب
  متصفحاً مفتوحاً لمستخدمٍ بالدور المناسب) — لتعمل الإشعارات ٢٤/٧ خادمياً.

## 1) الوضع الحالي (ما اكتُشف من الكود)

| البند | الواقع |
|---|---|
| المعمارية | SPA في `index.html`؛ Firebase compat 12.15.0 (app/auth/firestore/storage/app-check). مشروع `fast-buildings`. **لا Cloud Functions ولا Cloud Messaging ولا أي backend.** |
| الإشعارات الحالية | `HailNotify.js` = toast داخل الصفحة + Notification API للمتصفح فقط. لا ترسل شيئاً خارج الجهاز. |
| مشغّلات الإشعار الحالية | مستمعا `onSnapshot` في `index.html`: (أ) بلاغ جديد ~34275، (ب) طلب شراء جديد ~34301. **client-side** — تعمل فقط إن كان متصفح مستخدمٍ بالدور المناسب مفتوحاً. |
| الأدوار | حقل نصّي `role` في مستند `USERS` (**ليست** custom claims). الأدوار: `admin`, `project_manager`, `ceo`, `warehouse_manager`, `procurement_officer`, `finance`, `viewer`, `observer`. |
| الفنيون | تعريفان: (أ) قائمة ثابتة `WORK_TYPES`/`ALL_TECHS` في `index.html` (~6090)؛ (ب) مجموعة `technicians` (المعرّف = اسم الفني، الحقل الوحيد = `pin` مُجزّأ). **لا حقل هاتف.** |
| حقل الفني في البلاغ | `tech` = **اسم نصّي** (أو null)، لا معرّف. عند الإسناد تُضاف واقعة `timeline` والحالة تصير «قيد التنفيذ». |
| مجموعة البلاغات | `COLLECTION()` = `tickets` (+`_dev`). |
| مجموعة طلبات الشراء | `PURCHASES_COLLECTION()` = `global_purchases` (+`_dev`). |
| حالات طلب الشراء | آلة حالات غنية: `pending_pm` → `pm_approved`/`pm_rejected` → `wh_review`/`wh_reviewed` → `pending_proc` → `pending_ceo` → `pending_finance` → `proc_executing` → `wh_receiving`/`wh_auditing` → `closed`/`rejected`/`cancelled` (+ `pending_extra` للبنود الإضافية). |
| عتبة الاعتماد | `CEO_APPROVAL_THRESHOLD = 2000` (يُحيل ما ≥ العتبة للمدير التنفيذي). |
| الأمان | App Check مُفعّل (reCAPTCHA Enterprise) — يمكن فرضه على الـ Functions لاحقاً. |

## 2) المعمارية المقترحة (High-Level)

```
┌────────────────────────────────────────────────────────────────────┐
│  المتصفح (SPA — بلا تغيير جوهري)                                       │
│  يكتب/يعدّل مستندات tickets و global_purchases كالمعتاد               │
└───────────────┬────────────────────────────────────────────────────┘
                │ (كتابة عادية على Firestore)
                ▼
┌────────────────────────────────────────────────────────────────────┐
│  Firestore                                                          │
│  tickets/*            global_purchases/*                            │
└───────┬───────────────────────┬────────────────────────────────────┘
        │ onCreate / onUpdate    │ onUpdate (تغيّر status)
        ▼                        ▼
┌────────────────────────────────────────────────────────────────────┐
│  Cloud Function: notifyRouter  (Firestore-triggered)               │
│  ١. يكتشف الحدث (إسناد فني / تغيّر حالة PO / طلب جديد)                │
│  ٢. يحدّد المستلمين (خريطة الدور/المشروع → أرقام من USERS/technicians)│
│  ٣. يبني الرسالة من قالب معتمَد                                       │
│  ٤. يكتب مستند/مستندات في wa_outbox (مفتاح idempotent)               │
└───────────────┬────────────────────────────────────────────────────┘
                │ onCreate(wa_outbox/*)
                ▼
┌────────────────────────────────────────────────────────────────────┐
│  Cloud Function: waSender                                          │
│  يقرأ سرّ التوكن من Secret Manager → ينادي WhatsApp Cloud API        │
│  يحدّث حالة المستند: queued → sent → delivered/failed (+retry)       │
└───────────────┬────────────────────────────────────────────────────┘
                │ POST https://graph.facebook.com/.../messages
                ▼
        WhatsApp Cloud API (Meta)  →  هاتف الفني / المعتمِد
```

**لماذا طابور `wa_outbox` بدل الإرسال المباشر داخل المشغّل؟**
- **فصل المسؤوليات:** المشغّل يقرّر «مَن وماذا»، والمُرسِل يتكفّل بالشبكة والفشل.
- **موثوقية:** إعادة المحاولة، وسجل تدقيق كامل لكل رسالة (متى/لمن/الحالة).
- **منع التكرار:** مشغّلات Firestore *at-least-once* (قد تُطلق مرتين). نستخدم
  **معرّف مستند حتمي** = `hash(eventType + entityId + transitionKey + recipient)`
  فيُدمج التكرار في نفس المستند.
- **قابلية الإيقاف:** «مفتاح قتل» عام (`meta/wa_settings.enabled=false`) يوقف كل الإرسال فوراً.

## 3) نموذج البيانات (إضافات Firestore)

### 3.1 حقول الهاتف والموافقة
```
technicians/{name} :  + phone: "+9665XXXXXXXX"   (E.164)
                      + waOptIn: true|false
                      + waConsentAt: Timestamp
USERS/{uid}        :  + phone: "+9665XXXXXXXX"
                      + waOptIn: true|false
                      + notifyPrefs: { poNew:true, poApproval:true, ticket:true }
```
> **ملاحظة الربط:** الفني مُعرّف بالاسم في `tech`. مطابقة الرقم = `technicians/{tech}`.
> يجب توحيد الأسماء (trim/تطبيع) لتفادي عدم التطابق.

### 3.2 صندوق الصادر `wa_outbox/{idempotencyId}`
```
{
  to: "+9665...",           recipientRef: "USERS/uid" | "technicians/name",
  template: "ticket_assigned",   params: ["أحمد","TKT-2041","كهرباء","مبنى A","عاجل"],
  event: { type:"ticket_assigned", entityId:"TKT-2041", transition:"tech_set" },
  status: "queued",         // queued → sent → delivered | failed | skipped
  attempts: 0,   lastError: null,
  providerMessageId: null,
  createdAt, sentAt, updatedAt
}
```

### 3.3 إعدادات وسجل
```
meta/wa_settings : { enabled:true, provider:"meta", quietHours:{from:22,to:7},
                     dedupeWindowMin:10, roleRouting:{...} }
wa_log/{auto}    : أرشيف نهائي لكل محاولة (للتدقيق واللوحات).
```

## 4) الأحداث والتوجيه (Routing)

### 4.1 إشعار الفني ببلاغه — «إسناد فني»
- **المشغّل:** `onUpdate(tickets/*)` عندما يتغيّر `tech` من قيمة إلى أخرى (أو من null)،
  وكذلك `onCreate` إن أُنشئ البلاغ ومعه فنيّ مُسنَد مباشرة.
- **المستلم:** `technicians/{tech}.phone` (إن وُجد و`waOptIn=true`).
- **القالب:** `ticket_assigned`.
- **حماية:** لا نرسل إن كان `tech` لم يتغيّر فعلياً، ولا عند التغيير إلى null.

### 4.2 إشعار المعنيين بطلب شراء جديد
- **المشغّل:** `onCreate(global_purchases/*)`.
- **المستلمون:** أصحاب الدور المعنيّ بالمرحلة الابتدائية `pending_pm` = **مدير مشروع الطلب**
  (+ `admin` اختيارياً). لو تجاوز العتبة يُنبَّه المعنيّون بذلك مبكراً حسب السياسة.
- **القالب:** `po_new`.

### 4.3 إشعار «طلب يحتاج اعتمادك» — قلب الميزة
- **المشغّل:** `onUpdate(global_purchases/*)` عند تغيّر `status`.
- **خريطة الحالة → الدور المطلوب اعتماده** (قابلة للتهيئة في `meta/wa_settings.roleRouting`):

| الحالة الجديدة | مَن يُنبَّه (الدور) | القالب |
|---|---|---|
| `pending_pm` | `project_manager` (لمشروع الطلب) | `po_approval_needed` |
| `wh_review` | `warehouse_manager` | `po_approval_needed` |
| `pending_proc` | `procurement_officer` | `po_approval_needed` |
| `pending_ceo` | `ceo` | `po_approval_needed` |
| `pending_finance` | `finance` | `po_approval_needed` |
| `pending_extra` | `admin` + `ceo` | `po_extra_decision` |

- **إشعار صاحب الطلب** (تحديث حالة) عند: `pm_approved`/`pm_rejected`, `wh_reviewed`/`wh_rejected`,
  `ceo_rejected`, `finance_returned`, `proc_executing`, `closed`, `rejected`, `cancelled`
  → القالب `po_status_update` إلى منشئ الطلب (`createdBy`/`reporter`).

- **تحديد المستلمين حسب الدور:** استعلام `USERS where role == <الدور> and waOptIn == true`.
  - **قصر النطاق على المشروع:** لو كان للطلب `project`، يُفضَّل تنبيه مدير ذلك المشروع فقط.
    يتطلب حقل ربط في `USERS` (مثل `projects: [...]`) — **بند مفتوح** (انظر §9).

## 5) قوالب الرسائل (Message Templates)

> Meta تشترط قوالب **معتمَدة مسبقاً** لأي رسالة يبدأها العمل خارج نافذة الـ ٢٤ ساعة.
> كل هذه الإشعارات «مُبادِر بها العمل» ⇒ **دائماً عبر قوالب**. الفئة المناسبة: **Utility**.

أمثلة (عربية، مع متغيرات `{{n}}`):

- **`ticket_assigned`**
  `مرحباً {{1}}، تم إسناد بلاغ صيانة إليك.\nرقم: {{2}}\nالنوع: {{3}} — المبنى: {{4}}\nالأولوية: {{5}}`
- **`po_new`**
  `طلب شراء جديد {{1}} بقيمة {{2}} ر.س للمشروع {{3}} بانتظار المراجعة.`
- **`po_approval_needed`**
  `طلب الشراء {{1}} بقيمة {{2}} ر.س بانتظار اعتمادك ({{3}}). المشروع: {{4}}.`
- **`po_status_update`**
  `تحديث طلب الشراء {{1}}: الحالة الآن «{{2}}».`
- **`po_extra_decision`**
  `طلب الشراء {{1}} يحتوي بنداً إضافياً بقيمة {{2}} ر.س يحتاج البتّ فيه من صلاحيتك.`

> يمكن لاحقاً إضافة **زر رابط** في القالب يفتح الطلب/البلاغ مباشرة في النظام (deep link).

## 6) الأمان والامتثال

- **الأسرار:** توكن واتساب و`phone_number_id` في **Secret Manager** فقط، تُحقن في الـ Function.
  **لا شيء منها في المتصفح** إطلاقاً.
- **قواعد Firestore:** منع الكتابة على `wa_outbox`/`wa_log` من العميل (يكتبها Admin SDK فقط
  الذي يتجاوز القواعد)؛ السماح بالقراءة لـ `admin` فقط للوحة التدقيق.
- **App Check:** فرضه على أي Callable Function مستقبلية (إدارة الأرقام مثلاً).
- **الموافقة (Opt-in):** لا نرسل إلا لمن `waOptIn=true`؛ نحفظ `waConsentAt`.
  ندعم **إلغاء الاشتراك** (رد «إيقاف/STOP» → `waOptIn=false`).
- **ساعات الهدوء:** احترام `quietHours` (تأجيل غير العاجل).
- **الخصوصية:** لا نضع بيانات حسّاسة زائدة في نص الرسالة (المبالغ حسب السياسة).

## 7) الموثوقية والتشغيل

- **منع التكرار:** معرّف مستند حتمي في `wa_outbox` (§2). المُرسِل يتخطّى `status != queued`.
- **إعادة المحاولة:** تصعيد أُسّي (2s/4s/…)، حد أقصى للمحاولات ثم `failed` + تنبيه للأدمن.
- **معدّل الإرسال:** احترام حدود المزوّد (تجميع/تهدئة عند الدفعات الكبيرة).
- **المراقبة:** لوحة في النظام تقرأ `wa_log` (أُرسل/سُلّم/فشل) + تنبيه على الفشل المتكرر.
- **مفتاح القتل:** `meta/wa_settings.enabled=false` يوقف كل شيء فوراً.

## 9) القرارات المعتمَدة والبنود المفتوحة

### قرارات معتمَدة (2026-07-23)
- ✅ **المزوّد: WhatsApp Cloud API من Meta.** السبب: رسائل معاملاتية (Utility) بحجم متوسط
  ⇒ تسعير Meta المباشر أوفر، وتكامل مباشر مع Functions (استدعاء REST لـ Graph API).
  الإعداد الأوّلي الأطول (توثيق الرقم + اعتماد القوالب) يحدث **مرة واحدة**.
- ✅ **خطة Blaze متاحة** ⇒ نمضي بمعمارية Cloud Functions داخل نفس مشروع `fast-buildings`.
- ✅ **حالياً: الخطة تكفي** — لا كود إنتاجي بعد؛ التنفيذ يبدأ عند طلبٍ صريح.

### بنود ما تزال مفتوحة
1. **قصر التنبيه على المشروع:** هل نُنبّه *كل* من يحمل الدور، أم مدير/معنيّ **المشروع المحدد** فقط؟
   الثاني يتطلب ربط `USERS` بالمشاريع (`projects: [...]`).
2. **نطاق المرحلة الأولى:** نبدأ بـ«إسناد الفني» فقط ثم نتوسّع لاعتماد الشراء — أم الاثنان معاً؟
3. **جمع الأرقام والموافقات:** كيف نجمع أرقام الفنيين/المستخدمين ونوثّق موافقتهم (opt-in) عملياً؟
4. **العتبات في الرسائل:** هل نُظهر المبالغ في نص الواتساب أم نكتفي برقم الطلب لأسباب الخصوصية؟

## 10) ملاحظات تكامل مع الكود القائم

- نُبقي `HailNotify` كما هو (إشعار داخل التطبيق) — واتساب **طبقة مكمّلة** لا بديلة.
- ننقل منطق «مَن يُنبَّه» إلى الخادم (مشغّلات Firestore) بدل `onSnapshot` client-side،
  فتعمل الإشعارات دون اعتماد على متصفح مفتوح.
- إعادة استخدام الثوابت المركزية منطقياً على الخادم: `PO_CLOSED_STATUSES`،
  `CEO_APPROVAL_THRESHOLD`، تسميات الحالة `poStatusLabel` — يُفضّل **مصدر واحد للحقيقة**
  (ملف مشترك أو جدول تهيئة في `meta/`) لتفادي تكرار القوائم بين العميل والخادم.
- تحديث `NOTES.md` و`hail-tests` عند التنفيذ (اختبارات توجيه المستلمين ومنع التكرار).

## 11) قائمة تدقيق الإعداد الأوّلي (Onboarding — لمرة واحدة)

> إعداد حساب Meta والرقم والقوالب. يُنفَّذ **مرة واحدة** قبل الإطلاق الفعلي (Production).
> **ملاحظة مفصلية:** المطلوب هو **WhatsApp Cloud API / Platform** (يُدار من Business Manager
> ويُرسل برمجياً) — **وليس** تطبيق «WhatsApp Business» على الجوال (لا يُؤتمت).

### أ) قبل شراء أي خط — يبدأ التطوير مجاناً
- [ ] إنشاء **Meta Business Account** (Business Manager) باسم الشركة.
- [ ] إنشاء تطبيق في **Meta for Developers** وإضافة منتج **WhatsApp**.
- [ ] استخدام **رقم Meta التجريبي المجاني** (يُمنح تلقائياً) لبناء واختبار المنظومة —
      يرسل حتى **٥ أرقام مُسجّلة مسبقاً**، بلا حاجة لشراء خط.
- [ ] الحصول على **Access Token** تجريبي و**Phone Number ID** للاختبار.

### ب) شروط الخط الجديد (عند الإطلاق)
- [ ] **رقم مخصّص للنظام** (يُفضَّل جديد) — لأنه بعد ربطه بـ Cloud API **لا يعمل**
      في تطبيق واتساب العادي إطلاقاً. لا تستخدم رقماً شخصياً أو رقم الشركة المستعمل.
- [ ] الرقم **غير مُفعّل** على أي حساب واتساب (عادي/Business App). إن كان مُفعّلاً → احذف
      حساب واتساب لذلك الرقم أولاً.
- [ ] الرقم قادر على استقبال **رمز تحقق OTP** (SMS أو مكالمة) **مرة واحدة** وقت التسجيل.
- [ ] خط **مسبق الدفع رخيص يكفي**؛ يُنصح بإبقائه فعّالاً تحسّباً لإعادة تحقق مستقبلية
      (لا يحتاج شريحة في جهاز دائماً — الاستضافة عند Meta).

### ج) ربط الرقم واعتماد الهوية
- [ ] إضافة الرقم في **Business Manager → WhatsApp** وتحقيقه بالـ OTP.
- [ ] **توثيق الشركة** (Business Verification) — لرفع حدود الإرسال فوق الطبقة الأولى.
