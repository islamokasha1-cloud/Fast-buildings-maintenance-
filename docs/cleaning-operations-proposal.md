# مقترح — الإدارة التشغيلية لمشاريع النظافة

> **الحالة:** مقترحٌ للمراجعة قبل التنفيذ. مبنيٌّ على فحص المحرّك التشغيلي القائم (البلاغات +
> الخطط الوقائية + الأصول + تطبيق الفنيين) لا على تصوّرٍ نظري.
> **يكمل:** `docs/cleaning-project-management-plan.md` (الجانب المالي — نُفِّذ في v18.9uf).

---

## ٠) الاكتشاف الحاكم: المحرّك التشغيلي **موجود ومعزول لكل مشروع تلقائياً**

كل مجموعات النظام تأخذ بادئة معرّف المشروع عبر `_pfx()` و`_meta()` (`index.html:6702`):

```js
function _pfx(col){ return CURRENT_PROJECT ? CURRENT_PROJECT.id+"_"+col : col; }
function COLLECTION()    { return _pfx("tickets");    }   // {projectId}_tickets
function PPM_COLLECTION(){ return _pfx("ppm_plans");  }   // {projectId}_ppm_plans
function _meta(doc)      { return "meta/"+CURRENT_PROJECT.id+"_"+doc; }
```

**النتيجة:** مشروع النظافة **يحصل على مجموعة بلاغاته وخططه وإعداداته تلقائياً** بمجرّد
إنشائه — بلا أي بنيةٍ جديدة. فلا نبني نظاماً موازياً، بل **نُلبِس المحرّك القائم لغةَ النظافة**.

### جدول إعادة الاستخدام (ما هو جاهزٌ فعلاً)

| الصيانة | الآلية القائمة | جاهزيته للنظافة |
|---|---|---|
| البلاغات | `{projectId}_tickets` | ✅ **جاهز** — مجموعة مستقلة تلقائياً |
| الخطط الوقائية | `{projectId}_ppm_plans` + `nextDueDate`/`lastExecuted` | ✅ **جاهز** — ومنه التكرار |
| التكرارات | `PPM_FREQ_DAYS` = يومي/أسبوعي/شهري/ربع/نصف/سنوي | ✅ **«يومي» موجودٌ أصلاً** — قلب النظافة |
| أنواع العمل | `meta/{projectId}_settings.workTypes` | ✅ **جاهز** — نبذر أنواع نظافة |
| المباني/الأدوار | `BUILDINGS` + `getPPMBuildingFloors` | ✅ جاهز — المبنى/الدور = منطقة النظافة |
| قوائم الفحص | `ticket.checklist[{status:"done"}]` (`index.html:9416`) | ✅ **جاهز** — بنودٌ ونسبةُ إنجاز وشريط تقدّم |
| الأولويات/SLA | `PRIORITIES` + `SLA` | ✅ جاهز — زمن استجابة الشكوى |
| تطبيق ميداني | `tech-app.html` بدخول PIN + منتقي مشروع (v5.22) | ✅ جاهز — المشرف/العامل بدل الفني |
| الحضور | `attendance` (`checkIn`/`checkOut`، معرّف `اسم_تاريخ`) | ⚠️ موجود لكنه **عامٌّ لا مربوطٌ بمشروع** |

> **الخلاصة:** ~٨٠٪ من التشغيل جاهزٌ بإعادة الاستخدام. الجديد الحقيقي ثلاثة مفاهيم فقط (§٣).

## ١) الترجمة المفاهيمية (صيانة ⟵ نظافة)

| مفهوم الصيانة | مقابله في النظافة | ملاحظة |
|---|---|---|
| **بلاغ عطل** | **ملاحظة/شكوى نظافة** | نفس المحرّك: «دورة مياه الدور ٣ غير نظيفة» — من العميل أو جولة المشرف |
| **نوع العمل** (كهرباء/سباكة) | **نوع عمل النظافة** (دورات مياه/أرضيات/زجاج/نفايات/واجهات) | تبذيرٌ في `workTypes` |
| **الفني** | **عامل النظافة / المشرف** | نفس حقل `tech` وتوزيعه |
| **الخطة الوقائية** | **مهمة نظافة دورية** | نفس `ppm_plans` — لكن أغلبها **يومي** لا شهري |
| **الأصل** (مصعد/مكيّف) | **المنطقة/الموقع** (لوبي، دورات مياه ٣أ، مواقف) | وحدةٌ مكانية بدل معدّة |
| **الامتثال الوقائي %** | **نسبة تنفيذ الجدول اليومي** | نفس الحساب |

**الفرق الجوهري الباقي:** الصيانة **تفاعلية** (تنتظر البلاغ)، والنظافة **استباقية بالكامل** —
٩٥٪ من عملها جدولٌ يومي مخطَّط، والشكوى استثناءٌ يدلّ على خللٍ في التنفيذ. لذلك تنقلب
أولوية الشاشات: **الجدول اليومي هو الشاشة الرئيسية**، والشكاوى شاشةٌ ثانوية (عكس الصيانة).

## ٢) المقترح: ثلاث شاشات تشغيلية لمشروع النظافة

### 🟢 (أ) الجدول اليومي / لوحة التشغيل — *الشاشة المحورية*
بديل «الخطط الوقائية»، مبنيٌّ على نفس `{projectId}_ppm_plans`:
- **بطاقة اليوم:** كم مهمة مستحقة اليوم؟ كم نُفِّذت؟ كم متأخّرة؟ **نسبة التغطية %**.
- عرضٌ مجمَّع **حسب المنطقة** (لا حسب المعدّة): لوبي / دورات مياه / مواقف / واجهات…
- كل مهمة: المنطقة + نوع العمل + التكرار + المسؤول + آخر تنفيذ + الاستحقاق التالي.
- **التنفيذ بقائمة فحصٍ وصورة** (يعيد استخدام `checklist` القائم).
- **توليد الجدول بالذكاء الاصطناعي** (يعيد استخدام `_aiText` كما في الجدول الزمني للمقاولات):
  المستخدم يُدخل نوع المبنى ومساحاته وعدد الأدوار → النموذج يقترح **جدول مهام دورية كامل**
  (يومي/أسبوعي/شهري) بصيغة JSON، ثم يحرّره المستخدم. يوفّر ساعات إدخالٍ يدوي.

### 🟡 (ب) ملاحظات وشكاوى النظافة
نفس محرّك البلاغات (`{projectId}_tickets`) بلغة النظافة:
- مصدر الشكوى: **العميل / جولة المشرف / تفتيش داخلي**.
- الأولوية وSLA قائمان (شكوى حرجة = ساعتان).
- **صورة قبل/بعد** إلزامية للإغلاق (المرفقات قائمة).
- ربطٌ بالمنطقة وبالعامل المسؤول عنها ⟵ يكشف **المناطق المتكرّرة الشكوى**.

### 🟠 (ج) الحضور والتغطية — *الجديد الحقيقي*
- حضور يومي للطاقم **مربوطٌ بالمشروع** (الحالي عامٌّ — §٣-١).
- **الحاضر مقابل المتعاقد عليه** ⟵ مؤشّر نقص العمالة (أخطر مؤشّرٍ في عقود النظافة:
  نقص العمالة = مخالفة عقدية مباشرة).
- **التغطية:** هل كل منطقة نالت مهامها اليوم؟ منطقةٌ بلا تنفيذ = فجوةٌ حمراء.
- تنبيه واتساب عند نقص العمالة أو فجوة تغطية (طبقة الإشعارات قائمة).

## ٣) الجديد الحقيقي (ما لا مقابل له في الصيانة)

### ٣-١) الحضور مربوطاً بالمشروع
الحالي (`tech-app.html:713`) مجموعةٌ عامة `attendance` بمعرّف `الاسم_التاريخ` — لا تفصل
بين مشروعين. المقترح: `{projectId}_attendance` بنفس شكل المستند (`checkIn`/`checkOut`)
مع توافقٍ خلفيٍّ للقديم. تغييرٌ صغيرٌ يفتح متابعةَ طاقمٍ لكل عقد.

### ٣-٢) مفهوم «التغطية» (Coverage)
الصيانة لا تعرفه: بلاغٌ لم يأتِ = لا عمل. أمّا النظافة فـ**غياب العمل عن منطقةٍ = إخفاق**.
يحتاج حساباً جديداً: `مناطق نُفِّذت اليوم ÷ مناطق مستحقّة اليوم`.

### ٣-٣) جولة الجودة بالتقييم
تفتيشٌ دوريٌّ بدرجةٍ رقمية (١–٥ أو %) لكل منطقة + صور + مخالفات — يُنتج **اتجاه جودةٍ
شهرياً** يُعرض للعميل. لا مقابل له في الصيانة (التي تقيس زمن الاستجابة لا جودة النتيجة).

## ٤) أسلوب التنفيذ المقترح (مبدأ «لا انحدار»)

مشاريع الصيانة القائمة **يجب ألّا تتأثّر إطلاقاً**. لذلك:

1. **تفريعٌ حسب النوع لا استبدال:** الشاشات القائمة تبقى كما هي؛ مشروع النظافة يرى
   **تسمياتٍ وترتيباً وحقولاً** مختلفة عبر حارسٍ واحد `isCleaningProject()`.
2. **بذر الإعدادات عند التصنيف:** حين يُصنَّف مشروعٌ «إدارة نظافة» ولم تُضبط له
   `workTypes` بعد → تُبذَر أنواع عمل النظافة الافتراضية في `meta/{id}_settings`
   (قابلة للتعديل كالمعتاد). المشاريع القائمة لا تُمسّ.
3. **لا مجموعات جديدة إلا للجديد الحقيقي** (§٣) — الباقي يعيد استخدام القائم.
4. **وحدة مستقلة** `cleaning-operations.js` على نمط `stocktake.js` تحقن شاشاتها بنفسها،
   فلا يتضخّم `index.html` ولا نخاطر بمنطق الصيانة.

### أنواع عمل النظافة المقترحة (بذرة أولية — قابلة للتعديل)
| النوع | يشمل |
|---|---|
| نظافة دورات المياه | تعقيم، مستهلكات، تجفيف |
| نظافة الأرضيات | كنس، مسح، تلميع، جلي |
| نظافة الزجاج والواجهات | داخلي/خارجي |
| إدارة النفايات | تفريغ، نقل، حاويات |
| نظافة المكاتب والأثاث | تنظيف أسطح، تعقيم |
| المساحات الخارجية | مواقف، ممرات، حدائق |
| النظافة العميقة الدورية | سجاد، مجاري هواء، خزانات |
| أخرى | — |

## ٥) خارطة الطريق المقترحة

| المرحلة | المحتوى | القيمة |
|---|---|---|
| **٢-أ** | بذر أنواع عمل النظافة + الجدول اليومي (قراءة/تنفيذ بقائمة فحص) + لوحة اليوم | **الجدول اليومي يشتغل** — قلب التشغيل |
| **٢-ب** | توليد الجدول بالـ AI + التجميع حسب المنطقة | إدخالٌ في دقائق بدل ساعات |
| **٣-أ** | الحضور المربوط بالمشروع + الحاضر مقابل المتعاقد + التغطية | ضبط العمالة (أكبر تكلفة وأخطر مخالفة) |
| **٣-ب** | شكاوى النظافة بلغتها + صور قبل/بعد + المناطق المتكرّرة | رضا العميل |
| **٤** | جولات الجودة بالتقييم + اتجاه شهري + تقرير للعميل | إثبات الأداء وتجديد العقد |

## ٦) قراراتٌ مطلوبة قبل التنفيذ

1. **نقطة البدء:** المرحلة ٢-أ (الجدول اليومي) — أوصي بها لأنها قلب التشغيل؟
2. **المناطق:** نستخدم `BUILDINGS` + الأدوار القائمة كمناطق، أم نحتاج مستوى «منطقة» أدقّ
   (لوبي/دورات مياه/مواقف) تحت الدور؟
3. **الشكاوى:** ندمجها في شاشة البلاغات القائمة بلغةٍ مختلفة، أم شاشة مستقلة تماماً؟
4. **التطبيق الميداني:** يسجّل العامل تنفيذ مهامه من `tech-app.html` (بدخول PIN)، أم
   يكتفي المشرف بالتسجيل عن طاقمه في البداية؟
