# ربطُ Snyk بالمنصّة — دليلُ التشغيل

> **الخلاصة:** التكاملُ مكتوبٌ وجاهزٌ في `.github/workflows/snyk.yml`. ما يبقى عليك
> فعلُه **خطوةٌ واحدة**: وضعُ سرِّ `SNYK_TOKEN` في المستودع. وقبل وضعه لا يسقط أيُّ
> PR — الفحصُ يتخطّى نفسَه ويكتب سببَ التخطّي.

---

## ١) الخطوات (خمس دقائق)

1. **حسابٌ في Snyk:** [snyk.io](https://snyk.io) ← «Sign up with GitHub». الخطّةُ
   المجانية تكفي مستودعاً واحداً (حدودُها الشهرية على عدد الفحوص لا على الميزات).
2. **انسخ التوكِن:** في Snyk ← أيقونةُ الحساب ← **Account settings** ← **Auth Token**
   ← «click to show» ← انسخ.
3. **ضعه سرّاً في GitHub:** المستودع ← **Settings** ← **Secrets and variables** ←
   **Actions** ← **New repository secret**
   - الاسم: `SNYK_TOKEN`  ← **بالحرف، فسيرُ العمل يقرأ هذا الاسم تحديداً.**
   - القيمة: التوكِن المنسوخ.
4. **فعِّل Snyk Code (SAST):** في Snyk ← **Settings** (إعداداتُ المؤسسة) ← **Snyk Code**
   ← فعِّله. وهو **الطبقةُ الأهمُّ هنا** (السببُ في §٣)، ووظيفةُ `Snyk Code` في سير
   العمل تسقط برسالةٍ صريحةٍ إن كان مُطفأً.
5. **شغّل مرّةً يدوياً للتأكّد:** تبويب **Actions** ← «Snyk Security» ← **Run workflow**.

بعدها يعمل الفحصُ تلقائياً: عند كل PR، وعند كل دفعٍ إلى `main`، **وأسبوعياً** (الاثنين
٣:١٧ UTC) — والدورةُ الأسبوعية ليست ترفاً: الثغرةُ تُنشَر في تبعيةٍ **لم تتغيّر**،
فالفحصُ عند التعديل وحدَه لا يراها أبداً.

---

## ٢) طريقةٌ ثانيةٌ مكمِّلة: تكاملُ Snyk مع GitHub

ما سبق يشغّل Snyk **من داخل CI**. وهناك مسارٌ آخر يُستحسن تفعيلُه معه لا بدلاً منه:

Snyk ← **Integrations** ← **GitHub** ← **Connect** ← اختر `Fast-buildings-maintenance-`.

ما يضيفه على سير العمل:
- **لوحةُ متابعةٍ دائمة** لكل مشروعٍ في المستودع، وتنبيهاتُ بريدٍ عند ظهور ثغرةٍ جديدة.
- **Fix PRs تلقائية** — يفتح Snyk طلبَ دمجٍ يرفع الحزمةَ المصابة وحدَها.
- **Upgrade PRs** دوريةٌ لتحديث التبعيات.

والفرقُ عملياً: سيرُ العمل يفحص **اللحظة**، والتكاملُ يراقب **ما بين اللحظات**. وخطوةُ
`snyk monitor` في سير العمل (تعمل عند الدفع إلى `main` فقط) تودع لقطةَ الشجرة في اللوحة
نفسها، فتصلك التنبيهاتُ حتى لو لم تُفعِّل تكاملَ GitHub.

## ٣) ماذا يفحص Snyk في هذه المنصّة — وماذا **لا** يفحص

هذا القسمُ أهمُّ ما في الصفحة. «فحصُ المنصّة» عبارةٌ توحي بالشمول، والشمولُ غيرُ حاصل.

### يفحصه فعلاً

| الطبقة | ما تغطّيه هنا |
|---|---|
| **Snyk Code (SAST)** | كودُنا نحن: `index.html` · `tech-app.html` · كلُّ وحدات `.js` · `functions/` · `worker/`. يرصد XSS عبر `innerHTML` بمدخلٍ غيرِ مهرَّب، وأسراراً مكتوبةً في الكود، وتعابيرَ نمطيةً قاتلة (ReDoS)، ومسارات ملفّات. |
| **Snyk Open Source** | ثلاثُ شجرات تبعيات: الجذر (`jsdom` · `firebase-tools`…) · `functions/` (`firebase-admin` · `firebase-functions`) · `remotion/`. |

**ولمَ كان Snyk Code هو الأهمَّ هنا تحديداً؟** لأن المنصّة **ليست تطبيقَ npm**: لا
bundler ولا حزمَ تُستورَد في الإنتاج. فجردُ التبعيات — وهو ما يشتهر به Snyk — يغطّي
أدواتِ البناء والاختبار في الغالب، بينما **منطقُ العمل كلُّه كودٌ مكتوبٌ بيدنا**،
وهو ما يقرأه Snyk Code.

### لا يفحصه — ولا يُنبِّه إلى أنه لا يفحصه

1. **مكتباتُ الـCDN.** الملفّان `index.html` و`tech-app.html` يحمّلان — بوسمِ
   `<script src="https://…">` لا بـ`npm` — هذه المكتبات:

   | المكتبة | الإصدار | المصدر |
   |---|---|---|
   | Firebase (app · auth · firestore · storage · app-check) | `12.17.0` في `index.html` ⟂ **`10.12.0` في `tech-app.html`** | gstatic |
   | Chart.js | `4.4.1` | cdnjs |
   | SheetJS (`xlsx`) | `0.18.5` | cdnjs |
   | pptxgenjs | `3.12.0` | jsDelivr |

   **هذه خارجُ جردِ Snyk تماماً** — ليست في أيّ `package.json`، فلا تدخل الشجرة،
   ولا يُبلَّغ عنها لا بنعم ولا بلا. ولو صدرت ثغرةٌ في أيٍّ منها لبقيت اللوحةُ خضراء.
   وأبرزُ ما يستحقّ نظرةً بشرية: **`xlsx@0.18.5`** — حزمةُ SheetJS على npm متوقّفةٌ
   عند هذا الإصدار وانتقل مشروعُها إلى توزيعه الخاصّ، ونسخُ `0.18.x` تحمل ثغراتٍ
   معلومة: تلويثُ النموذج الأوّليّ (CVE-2023-30533 — يمسّ ما دون 0.19.3) وReDoS
   (CVE-2024-22363 — يمسّ ما دون 0.20.2). و**فرقُ إصدارِ Firebase بين الملفّين**
   (12.17.0 مقابل 10.12.0) بندٌ مستقلٌّ يستحقّ توحيداً.
   **العلاجُ إن أُريد أن يراها Snyk:** تُسجَّل هذه المكتبات في `package.json` (ولو
   بلا استعمالٍ برمجيّ) فتدخل الجرد، أو تُتابَع يدوياً في مراجعةٍ دورية. القرارُ
   للمالك — والمهمّ ألّا يُظنَّ أنها مفحوصة.

2. **`firestore.rules`.** ليست صيغةَ IaC مدعومةً من `snyk iac` (المدعومُ Terraform
   وKubernetes وCloudFormation وARM). وقواعدُ الأمن هنا **لا تُقرأ بالعين أصلاً**:
   تُقيَّم بـ«أو» عبر كل البلوكات المتطابقة، فقاعدةٌ عامّةٌ واحدةٌ تُبطل عشراً
   صارمةً بلا أن يظهر ذلك في أيّ سطر. حارسُها الوحيد المعتبَر:
   `npm run rules:check` — محاكي Firestore حقيقيّ (يعمل في CI ضمن `hail-tests.yml`).

3. **حرّاسُ الأدوار والمصادقة في التطبيق.** لا يعرفها ماسحٌ ساكن. حارسُها
   `auth-guard-check.mjs` و`users-guard-check.mjs` (الدورُ من التوكِن لا من الجلسة).

4. **بياناتُ Firestore وإعداداتُ مشروع Firebase وأسرارُ الـWorker.** خارجَ المستودع
   كلَّها.

> بعبارةٍ واحدة: **Snyk يضيف طبقةً لم تكن موجودة (SAST + جردُ التبعيات)، ولا يُلغي
> طبقةً قائمة.** الفحوصُ في `NOTES.md §5` تبقى هي الحارسَ على منطق العمل والأمن
> السلوكيّ.

## ٤) التشغيل محلياً

```bash
npm run snyk:code      # فحصُ الكود (SAST)
npm run snyk:deps      # فحصُ التبعيات في المشاريع الثلاثة
npm run snyk:monitor   # إيداعُ لقطةٍ في لوحة Snyk (لا يفحص — يراقب)
```

يحتاج توكِناً في البيئة قبل التشغيل:

```bash
export SNYK_TOKEN=…      # أو:  npx snyk auth   (يفتح المتصفّح مرّةً واحدة)
```

لفحص ملفٍّ أو مجلّدٍ بعينه:

```bash
npx snyk code test --severity-threshold=high contracts.js
npx snyk test --file=functions/package.json
```

## ٥) من فحصٍ تقريريٍّ إلى فحصٍ مانعٍ للدمج

سيرُ العمل **تقريريٌّ عمداً في بدايته**: يُبلِّغ ولا يُسقط. السبب أن إسقاط كلِّ PR من
اليوم الأول — والقائمةُ الأولى في مستودعٍ لم يُفحَص قطُّ تكون طويلة — يُعلِّم الفريقَ
تجاوزَ الفحص لا إصلاحَه.

بعد تصفيةِ القائمة الأولى، يُقلَب المفتاحُ في `.github/workflows/snyk.yml`:

```yaml
env:
  SNYK_SEVERITY: high            # low | medium | high | critical
  SNYK_FAIL_ON_ISSUES: 'true'    # ← كان false
```

ثم يُجعَل «Snyk Security» فحصاً مطلوباً: Settings ← Branches ← قاعدةُ `main` ←
**Require status checks to pass**.

---

## ٦) تجاهلُ نتيجةٍ (بقرارٍ موثَّق)

لا تُعدَّل النتيجةُ في الكود لإسكاتها. الطريقُ الصحيح يكتب سبباً وتاريخَ انتهاء:

```bash
npx snyk ignore --id=<معرّف-النتيجة> --reason="السببُ بجملةٍ مفهومة" --expiry=2026-12-31
```

يولّد ذلك ملفَّ `.snyk` في جذر المستودع — **يُلتزَم به في git** ليكون قرارُ التجاهل
مرئياً في المراجعة لا خياراً في لوحةِ شخصٍ واحد. والانتهاءُ (`--expiry`) مقصود: تجاهلٌ
بلا أجلٍ يصير نسياناً دائماً.

## ٧) عطلٌ متوقَّع وحلُّه

| العَرَض | السبب | الحلّ |
|---|---|---|
| كلُّ وظائف Snyk «skipped» | `SNYK_TOKEN` غير مضبوط، أو الـPR قادمٌ من fork (الأسرارُ لا تصل إليه) | ضع السرَّ · وللـfork: شغّل الفحص بعد الدمج أو من `workflow_dispatch` |
| `Snyk Code is not supported for org` | Snyk Code مُطفأٌ في إعدادات المؤسسة | فعِّله (§١ خطوة ٤) |
| `Authentication failed` | توكِنٌ منتهٍ أو منسوخٌ ناقصاً | أعِد نسخَه من Account settings |
| نتائجُ لا تظهر في تبويب Security | المستودعُ خاصٌّ بلا GitHub Advanced Security — رفعُ SARIF مرفوض | النتائجُ في سجلّ الخطوة وفي لوحة Snyk (رفعُ SARIF `continue-on-error` عمداً لهذا) |
| بطءٌ في وظيفة Snyk Code | `index.html` ~٢٫٨ ميغابايت في ملفٍّ واحد | متوقَّع؛ المهلةُ ٢٠ دقيقة |
