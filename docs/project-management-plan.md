> **اقرأني أولاً.** ده مستند **تصوّر للمراجعة والنقاش قبل كتابة أي كود**. الهدف نتفق على
> الشكل والحقول والمنطق على الورق، وبعدين ننفّذ صح من أول مرة. كل رقم أو مسمّى هنا
> **مبدئي وقابل للتعديل** — علّق عليه وعدّله زي ما تحب.
>
> **الحالة:** مسودّة ثانية — أُدرِجت قرارات صاحب النظام (§٠). لم يُكتب أي كود بعد.
> **الفرع:** `claude/bali-project-management-system-126929`
> **العملة:** ريال (SAR) — عملة واحدة لكل الأرقام المالية.

## ١) الفكرة في سطرين

نحوّل «المشروع» من مجرّد **اسم/وسم** بنعلّق عليه طلبات الشراء والبلاغات، إلى **بطاقة مشروع
حقيقية** فيها موازنة وتكلفة فعلية وإيراد وربحية وجدول زمني — مربوطة **أوتوماتيك بنظام
المشتريات الحالي**.

السؤال اللي المفروض النظام يجاوبه في شاشة واحدة:
> «المشروع ده بيكسّب ولا بيخسّر؟ صرفت كام من المخطط؟ فاضل كام؟ والعميل دفع كام؟ ومتأخر ولا لأ؟»

## ٢) المبادئ الحاكمة (مهمة)

1. **نبني فوق الموجود، مش من الصفر.** «المشروع» موجود أصلاً (`meta/projects`)، وكل طلب شراء
   مربوط بمشروع (`projectId`/`projectName`)، والمشتريات **بتحسب المصروف الفعلي لكل مشروع
   بالفعل** من الطلبات المغلقة (`poActualCost` + `poIsClosed`). إحنا بنضيف طبقة فوق، مش بنعيد.
2. **مصدر واحد للحقيقة.** المصروف الفعلي بييجي من دوال المشتريات المركزية الموجودة
   (`poIsClosed`, `poActualCost`, `_poPaidSoFar`) + دفعات العمالة الجديدة، فلا يوجد رقمان
   متناقضان. أي حساب جديد يمرّ على نفس الدوال.
3. **بنود موازنة هجينة.** بنود عامة ثابتة (عمود فقري للتقارير والربط) + تفاصيل مقايسة لكل
   مشروع تحتها (تفصيل ومرونة). (تفصيل في §٦).
4. **لا انحدار.** المشاريع الحالية (الأمانة `hail` وغيرها) تفضل تشتغل زي ما هي؛ الحقول
   الجديدة كلها **اختيارية** — مشروع بلا موازنة يظهر عادي بموازنة = صفر.
5. **إعادة استخدام السباكة الموجودة.** الذكاء الاصطناعي (`_aiText` + `meta/ai_settings`)،
   المرفقات (Storage)، نظام الأدوار، والإشعارات (`HailNotify`/واتساب) كلها موجودة ونعيد
   استخدامها بدل بناء جديد.
6. **التدرّج.** مراحل، كل مرحلة تشتغل لوحدها وتدّي قيمة، والبناء تراكمي.

## ٣) نموذج البيانات (مبدئي)

### ٣-١) بطاقة المشروع
نوسّع كائن المشروع في `meta/projects` (الموجود حالياً `{id, name, desc, icon}`) بحقول
اختيارية:

```
meta/projects  →  projects: [{
  id, name, desc, icon,            // الموجود حالياً — بدون تغيير
  client,                          // اسم العميل
  type,                            // "construction" | "renovation" | "maintenance"
  location,                        // الموقع (بالي / العنوان)
  managerUid,                      // مدير المشروع المسؤول
  status,                          // "planning" | "active" | "on_hold" | "closed"
  startDate, endDate,              // تواريخ مخطّطة (YYYY-MM-DD، تمرّ على _parseLocalDate)
  contractValue,                   // قيمة العقد الإجمالية (الإيراد المتوقّع) — بالريال
  createdAt, createdBy
}]
```
> **حقل `type`** هو اللي يفرز مشاريع المقاولات/الترميم في قسم «إدارة المشاريع» الجديد،
> بينما تظل كل المشاريع شغّالة عادي في الصيانة والمشتريات.

### ٣-٢) موازنة المشروع (مستند مستقل لكل مشروع)
```
meta/{projectId}_budget  →  {
  categories: [                    // البنود العامة الثابتة المفعّلة لهذا المشروع
    { key:"electrical", name:"كهرباء", planned: 120000 }, ...
  ],
  boq: [                           // بنود المقايسة التفصيلية (اختياري لكن مُوصى به)
    { id, categoryKey:"electrical", desc:"تمديد 3 فاز", qty, unit, unitPrice, planned },
    ...
  ],
  updatedAt, updatedBy
}
```
- `planned` للبند العام = مجموع بنود المقايسة تحته (تلقائي) **أو** رقم مُدخل يدوياً لو المشروع
  لسه مبيتفصّلش بمقايسة.
- ربط لاحق بمحرك تحليل الأسعار (`price-analysis.js`): بند المقايسة يتولّد من Rate build-up.

### ٣-٣) الإيراد والمستخلصات (مستند مستقل لكل مشروع)
```
meta/{projectId}_revenue  →  {
  extracts: [                      // المستخلصات (كل مستخلص له دورة اعتماد ٥ مراحل)
    { id, no, date, amount, desc,
      stage,                       // "tech_office" | "pm" | "projects_mgr" | "finance" | "ceo" | "approved" | "rejected"
      timeline: [{stage, by, at, note}],   // سجل زمني لكل خطوة (نفس فكرة timeline في طلب الشراء)
    }
  ],
  payments: [                      // دفعات العميل الفعلية الواردة
    { id, date, amount, ref, receiptUrl, by }
  ],
  updatedAt, updatedBy
}
```

**دورة اعتماد المستخلص (٥ مراحل):**
```
مكتب فني → مدير المشروع → مدير المشاريع → المالية → المدير التنفيذي → معتمد
tech_office   pm         projects_mgr    finance    ceo              approved
```
- كل مرحلة تعتمد أو ترفض (يرجّع للمرحلة السابقة أو للبداية)، ويُسجَّل كل انتقال في `timeline`.
- نفس فلسفة سلسلة اعتماد طلب الشراء الموجودة (`PO_STATUS` + `timeline`) — نعيد استخدام النمط.
- إشعار صاحب الدور الحالي عند كل انتقال (إعادة استخدام طبقة الإشعارات/واتساب).

### ٣-٤) دفعات العمالة (مفهوم جديد — مستند/مجموعة جديدة)
```
{projectId}_labor  (مجموعة)  →  كل مستند دفعة:
  { id, projectId, date, workerOrCrew, categoryKey:"labor",
    description, amount, ref, receiptUrl, by, createdAt }
```
- تدخل ضمن **المصروف الفعلي** للمشروع تحت بند «مصنعيات/عمالة» (§٦).
- وحدتها `labor-payments.js` (§٨). تربط اختيارياً بكتالوج العمالة الحالي (`labor-catalog.js`).

## ٤) أين يظهر في النظام (الملاحة)

النظام متمحور حول المشروع (تختار مشروع فيتفلتر كل شيء). مشاريع المقاولات/الترميم **هي نفس
كيان المشروع**، ونضيف **قسم قوائم جديد: «إدارة المشاريع»** جنب الأقسام الحالية (لوحة المعلومات /
الصيانة / المشتريات)، وجواه صفحات جديدة على نمط `id="page-..."` الحالي:

| الصفحة | الوظيفة |
|---|---|
| `page-projects` | قائمة المشاريع بالأرقام المالية (موازنة/مصروف/ربح + شريط لون) |
| `page-project-card` | بطاقة المشروع بالتبويبات (§٥) |
| `page-projects-dashboard` | لوحة إجمالية لكل الشركة + تنبيهات التجاوز |
| `page-labor-payments` | دفعات العمالة |

> المشروع نفسه يفضل شغّال عادي في الصيانة والمشتريات — إحنا بنضيف عدسة مالية/إدارية جديدة فوقه.

## ٥) بطاقة المشروع (الشاشة المحورية) — التبويبات

- **نظرة عامة:** ٤ بطاقات كبيرة (الموازنة / المصروف الفعلي / الإيراد / الربح) + شريط تقدّم
  مالي + بيانات العميل والعقد والتواريخ والحالة.
- **الموازنة:** جدول البنود العامة، وتحت كل بند بنود مقايسته، بالأعمدة:
  **الموازنة | المرتبط (طلبات جارية) | المصروف (مغلقة + عمالة) | المتبقّي | %**.
- **المشتريات:** طلبات الشراء المربوطة بالمشروع (مفلترة)، برابط مباشر للطلب في المشتريات.
- **الإيراد:** المستخلصات (بحالة الاعتماد ٥ مراحل) + دفعات العميل، ومقارنة مستحق/مُحصَّل.
- **الجدول الزمني:** توليد/تعديل/متابعة (§٩).
- **الربحية:** الإيراد − المصروف، بالمخطّط وبالفعلي، وهامش الربح %.

## ٦) بنود الموازنة الهجينة (معتمدة)

**قائمة عامة ثابتة (معتمدة):**

| المفتاح | البند | يشمل |
|---|---|---|
| `materials` | خامات عامة | مواد بناء أساسية |
| `plumbing` | سباكة | مواسير، تشطيبات صحية |
| `electrical` | كهرباء | تمديدات، لوحات، إنارة |
| `plaster` | محارة/بياض | — |
| `finishes` | تشطيبات | دهانات، أرضيات، سيراميك |
| `carpentry` | نجارة | أبواب، وحدات |
| `aluminum` | ألوميتال/زجاج | — |
| `labor` | مصنعيات/عمالة | من دفعات العمالة (§٣-٤) وكتالوج العمالة |
| `subcontractor` | مقاول باطن | بنود مسندة لمقاول |
| `equipment` | معدات/إيجارات | — |
| `overhead` | مصاريف إدارية | نقل، إشراف، متنوّع |
| `uncategorized` | غير مصنّف | التوافق مع الطلبات القديمة |

- **الثابت** = العمود الفقري (مقارنة بين المشاريع + ربط المشتريات + تقارير مجمّعة).
- **بنود المقايسة** = تحت كل بند عام، خاصة بكل مشروع.
- القائمة العامة قابلة للتعديل من لوحة الأدمن.

## ٧) الربط بالمشتريات + تنبيه التجاوز

### الموجود بالفعل
- طلب الشراء فيه `projectId` + `projectName`.
- المشتريات بتجمّع المصروف الفعلي لكل مشروع من `poIsClosed` + `poActualCost`.

### الإضافة المطلوبة
1. **حقل «بند الموازنة» على شاشة طلب الشراء**: بعد اختيار المشروع، قائمة منسدلة بالبنود العامة
   (واختياري: بند المقايسة). يُخزَّن `budgetCategoryKey` على الطلب.
2. **تجميع ثلاثي لكل بند:** المرتبط (`poStageIsWip`) / المصروف (`poActualCost` + دفعات العمالة)
   / المتبقّي = الموازنة − (المرتبط + المصروف).
3. **تنبيه تجاوز الموازنة — تحذيري فقط:** عند إنشاء/اعتماد طلب هيخلّي البند يعدّي موازنته →
   تحذير واضح **لا يمنع** الاعتماد (قرار ٢). خيار المنع مؤجَّل للأدمن لاحقاً.

> **توافق:** الطلبات القديمة بلا `budgetCategoryKey` تتجمّع تحت «غير مصنّف» فلا تختفي.

## ٩) الجدول الزمني بالذكاء الاصطناعي

يعيد استخدام `_aiText(messages, opts)` الموجودة (Claude عبر Proxy في `meta/ai_settings`).

**التدفّق:**
1. **توليد:** المستخدم يدخل (نوع المشروع، المساحة/النطاق، تاريخ البدء، المدة التقديرية، أهم
   البنود). الوحدة تبني رسالة للنموذج تطلب **خطة مراحل بصيغة JSON** (مرحلة، وصف، بدء، مدة،
   نسبة من المشروع، اعتماديات). نُلزم النموذج بمخطّط JSON ثابت فنقرأه بأمان.
2. **تخزين + تعديل:** الناتج يُحفظ في `meta/{projectId}_schedule` كمصفوفة مراحل قابلة للتحرير
   يدوياً (إضافة/حذف/سحب التواريخ) — الـ AI اقتراح أوّلي لا قيد.
3. **متابعة:** لكل مرحلة **نسبة إنجاز فعلية** يحدّثها مدير المشروع، ومؤشر تأخّر (مخطّط مقابل
   فعلي) — أخضر/أصفر/أحمر. عرض شريطي بسيط (Gantt مبسّط بالـ HTML/CSS، بلا مكتبات خارجية).

```
meta/{projectId}_schedule  →  {
  phases: [{ id, name, desc, start, durationDays, weight, progress, deps:[ids], status }],
  generatedByAI, updatedAt, updatedBy
}
```

## ١٠) خارطة الطريق (مراحل التنفيذ)

### 🟢 المرحلة ١ — الأساس المالي والربط بالمشتريات
توسيع بطاقة المشروع + شاشة الموازنة الهجينة + حقل «بند الموازنة» على طلب الشراء + التجميع

### 🟡 المرحلة ٢ — الإيراد والربحية ودفعات العمالة

اللوحة الإجمالية للشركة.

### 🟠 المرحلة ٣ — الجدول الزمني والتنفيذ
توليد الجدول بالـ AI + التحرير اليدوي + متابعة نسب الإنجاز ومؤشر التأخّر + تقارير موقع بالصور.

## ١١) الأدوار والصلاحيات (مبدئي)

| الدور | الصلاحية |
|---|---|
| الأدمن | إنشاء/تعديل/حذف المشاريع + تعديل البنود العامة |
| مدير المشروع | تعديل موازنة وبيانات مشاريعه + نسب الإنجاز + بدء المستخلص |
| مدير المشاريع | اعتماد مرحلته في المستخلص + متابعة كل المشاريع |
| المالية | دفعات العميل + دفعات العمالة + مرحلتها في المستخلص + الربحية |
| المدير التنفيذي | الاعتماد النهائي للمستخلص |
| مكتب فني | بدء/إعداد المستخلص (المرحلة الأولى) |
| viewer | قراءة فقط |

> يُبنى فوق نظام الأدوار الحالي (`request.auth.token.role`) وقواعد Firestore الموجودة. قد
> نحتاج إضافة أدوار جديدة (مكتب فني/مدير مشروع) لسلسلة المستخلص.

## ١٢) نقاط تحتاج توضيحاً قبل التنفيذ

1. **الأدوار الجديدة:** «مكتب فني» و«مدير المشروع» و«المدير التنفيذي» — موجودة كأدوار في
   النظام حالياً ولا ننشئها؟ (مهم لسلسلة اعتماد المستخلص).
2. **دفعات العمالة:** تُدخَل يدوياً بمبلغ، ولا مرتبطة بحضور/أيام عمل (attendance موجود)؟
3. **بند الموازنة على الطلب:** إلزامي لكل طلب جديد، ولا اختياري مع افتراض «غير مصنّف»؟
4. **الجدول الزمني:** Gantt مبسّط بالـ HTML يكفي، ولا محتاج عرض أكثر تفصيلاً؟

## ملاحظات تقنية للتنفيذ

- المصروف الفعلي **لا يُخزَّن** — يُحسب لحظياً من طلبات الشراء + دفعات العمالة (مصدر واحد للحقيقة).
- رفع الإصدار `APP_VERSION` + cache-busters عند التنفيذ (يفحصها `hail-tests.js`).
- قواعد Firestore: `meta/{id}_budget`/`_revenue`/`_schedule` و`{id}_labor` تحت القاعدة العامة
  (`hasRole`)؛ إضافة صريحة فقط عند الحاجة لوصول خاص.
- كل الأرقام بالريال (SAR)، تنسيق موحّد عبر دالة العرض الحالية.
